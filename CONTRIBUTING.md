# Contributing

1. **Generic only.** No client, employer, product or system names; no people; no figures, error
   codes, hostnames or tenants from a real engagement. Write "an e-commerce booking flow", not
   the name of the system.
2. **Text sources only.** Markdown, shell, Python, CSS, YAML. No PDFs, slides, spreadsheets,
   HAR captures or exports — the guardrails reject them. Test fixtures are YAML or Markdown under
   `tools/tests/fixtures/` (not in the build), or are generated by the test at run time; tool
   output never goes into this repository.
3. **Run the guardrails, the lint and the tool tests before every commit:** `scripts/guardrails.sh`
   (with the consistency check, `scripts/consistency.py`), `scripts/lint.sh`, `scripts/test-tools.sh`. The denylist (one term per line) lives in a private file
   outside this repository; `scripts/sync-denylist.sh [path]` puts it into the
   `GUARDRAIL_DENYLIST` secret and into the git-ignored `.guardrails-denylist` for local runs. A pull request from a fork gets no secrets, so its CI runs the
   public checks and skips the denylist; the maintainer runs the denylist locally before
   merging, and pushes to `main` and every release require it.
   On a pull request, CI also writes `scripts/word-delta.sh` output to the job summary.
   The assembled stage prompts are pinned in `tools/tests/fixtures/prompts/`. After a deliberate
   prompt change, refresh them with `UPDATE_GOLDEN=1 tools/tests/test_prompt.sh`; the pull
   request says why the prompts changed.
4. **A new file** goes into `scripts/files.sh`, under its part, or the guardrails fail;
   `tools/tests/test_files.sh` checks the order rules.
5. **Release:** raise the version in the README status table, move the `Unreleased` entries of
   `CHANGELOG.md` under a heading for that version (the release notes are taken from it, and the
   guardrails fail without it), merge to `main`, then tag
   `vX.Y.Z` on `main`. The release workflow re-runs the guardrails, checks the tag against the
   README, builds the PDF, checks the PDF text, and attaches it to the GitHub release.
6. Build locally with `scripts/build.sh --downloads` (needs pandoc and weasyprint). Another edition
   (own title, author, footer, file list, extra chapters) is built from a repository that holds
   this one as a git submodule: `kit/scripts/build.sh --config edition.conf`.

## Requirements

| For | Needs |
|---|---|
| The tools and their tests | bash, git, Python 3 with PyYAML (`pip install -r requirements.txt`), jq |
| The PDFs (`scripts/build.sh`, `tools/report-pdf.sh`) | pandoc, weasyprint, and poppler (`pdftotext`, `pdffonts`) |
| The guardrails | gitleaks (skipped locally when absent, required in CI) |
| The lint (`scripts/lint.sh`) | shellcheck, ruff (skipped locally when absent, required in CI) |

`scripts/ci-install.sh` pins the versions CI uses. Without pandoc, weasyprint or poppler the
tests that build a PDF say "skipped" and the rest run; with `KIT_REQUIRE_PDF_TOOLS=1`, as in
CI, a missing one fails. The PDF scripts check for their tools before they start and name the
missing ones.
